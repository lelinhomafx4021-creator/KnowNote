## 管理员如何认定

1. ADMIN_EMAILS 逗号分隔、去空白、转小写；启动、注册、登录时将匹配用户设为 admin。
2. 未配置名单且数据库没有任何管理员时，按 created_at/id 找最早注册用户成为管理员；注册与角色修改使用数据库 advisory 事务锁，避免并发越过数量约束。
3. 普通用户默认 user、disabled=false。JWT 只带用户标识，业务请求每次查库确认账号未停用，管理员接口再查 role。角色撤销、停用对后续旧 token 请求立即生效。
4. 不能停用自己、撤销自己的管理员权限，系统必须保留至少一位可用管理员。环境名单用户被手工撤权后，下次登录/启动会重新认定，永久撤权需同步调整部署环境。

## 后台可修改的配置

| 分组 | 白名单 |
|---|---|
| 对话 | CHAT_BASE_URL、CHAT_API_KEY、CHAT_MODEL、CHAT_MODELS |
| 向量 | EMBED_BASE_URL、EMBED_API_KEY、EMBED_MODEL |
| 额度 | QUOTA_DAILY_CHAT_REQUESTS、QUOTA_DAILY_TOKENS（0 为不限） |

不开放 EMBEDDING_DIM、存储、TTS 或图像配置。数据库值优先于启动环境，后者保留旧 LLM_* 回退，再到内置默认。密钥用 SETTINGS_ENCRYPTION_KEY 的 SHA-256 作 AES-GCM 主密钥，未配置则由 JWT_SECRET 派生；随机 nonce，接口仅前 3 + 后 4 掩码，短密钥全隐藏。解密失败时不会崩溃，来源标签反映回退层。

## 热更新原理

保存先合并候选配置并校验，再测试受影响的对话/向量能力；对话发极短消息，向量嵌入短文本并校验数据库固定维度，总预算 15 秒。失败不写配置或审计；通过后先将配置与键名审计写入事务，再 atomic.Pointer 替换 Provider 快照。Guard 在一次调用开始时固定客户端，正在进行的流继续持有旧客户端，下一次能力调用取得新客户端；额度在每次准入读取当前配置。仅额度更新不请求模型。

向量模型或地址实际改变时返回并显示重建提示。重建固定启动时的向量客户端，复用原重建事务；期间资料读写可能等待，失败整体回滚。向量调用按资料原用户记用量，重建过程中仍可调整额度。进度为已有分块数，处理中 completed 为尚未提交的处理量。
